A customer moves a rollout from Friday to Monday. The project record says Monday. The agent still schedules around Friday.

I’d look for a summary that was generated from the old state and carried forward through several compactions. Each round can faithfully preserve a stale answer.

One way to reduce that drift is to make summaries rebuildable. Keep source references and versions for each segment. A rollout digest can depend on separate schedule, access, and training records. If the schedule changes, rebuild that segment from its source and refresh the parent digest that depends on it.

Where do checksums help? They can tell the harness that the inputs to a cached summary changed. They can’t tell you whether the summary captured the customer’s intent. That takes an eval: correct the source date, trigger two more compactions, then check which date the agent uses and which record it cites.

I’d start with explicit revisions and a single derived summary. A dependency tree earns its place when updates are frequent and rebuilding the full digest materially costs time or money.

### Build a correction you can replay

Take three records contributing to the same handoff digest: schedule revision 7, access revision 3, and training revision 4. When the project lead changes the launch date, the schedule moves to revision 8. The digest generated from revision 7 is now stale even if it is internally consistent.

I’d store each digest with the ordered revisions of its inputs and the versions of the extraction schema, prompt, and model configuration. For a three-part handoff, the root records the three child revisions. A schedule change rebuilds the schedule digest from the authoritative record and then rebuilds the root. Access and training can be reused.

A race can still undo the fix. Say a worker starts a revision-7 rebuild, then pauses while the revision-8 build finishes. On commit, compare the worker’s expected revision with the current source revision. Reject the old result if they differ. For an action that depends on the launch date, resolve the current date from the scheduling system before acting.

### Measure the cost of invalidation and the quality of the result

First measure how often sources change and how much a full regeneration costs. A single digest plus a version check is easier to operate for a small account record. A dependency tree helps when independent sections update frequently and materializing the whole summary is expensive. Track the number of derived nodes rebuilt per update and how long users can receive a stale answer.

For fidelity, run Friday → Monday → Tuesday through two compaction cycles. Ask for the current date and what was previously agreed. Score both answers against the relevant source IDs. A matching hash is evidence that the declared inputs match. The replay tells you whether the summary used them correctly.

**Try it.** Advance one source revision and verify exactly which keys change. Then test a stale worker result arriving after the new summary.

## Conclusion

Version inputs so you can reject stale builds, and replay a correction so you can prove it changes the agent’s decision. That combination covers freshness and fidelity.
