An agent that needs my approval for a $12,400 refund shouldn't send me four paragraphs. It should send me the evidence and three buttons.

Most AI agents in production today still answer in text. That made sense when the agent was a chatbot. It makes much less sense now that agents pull data from five systems, prepare decisions and wait for a person to sign off. The person on the other end doesn't need a well-written summary. They need the next screen: the table to scan, the form to confirm, the button that commits the decision.

That idea has a name, generative UI. I wanted to know how practical it is today, so I spent some evenings building a small prototype on [OpenUI](https://github.com/thesysdev/openui), an open-source framework from Thesys under the MIT license. Everything below uses mock data. The companies, people and numbers are made up.

## How OpenUI works

The model doesn't write HTML or React, and it doesn't fill in a JSON schema for one fixed widget. The flow has four steps:

1. **You define a component library.** Cards, tables, charts, forms, buttons, callouts, each with a typed set of arguments. This list is the only vocabulary the model gets.
2. **OpenUI turns that library into the system prompt.** You don't hand-write instructions for every component. The prompt is generated from the same definitions the renderer uses, so the two can't drift apart.
3. **The model streams OpenUI Lang**, a compact, line-by-line language. Each line names one piece of the interface.
4. **The renderer draws the UI as the tokens arrive.** The interface assembles itself on screen while the model is still writing.

Here is a trimmed piece of what the model produced for the refund case:

```text
root = Card([title, gate, facts, recChart, rec, decision])
title = CardHeader("Refund request: Acme Health", "Ticket #48213, received today 09:12")
gate = Callout("warning", "Needs a human: $12,400 is above my $2,000 approval limit", "I checked the contract, usage and refund policy.")
recChart = BarChart(["Full refund", "Downgrade + partial", "Decline"], [cost], "grouped", "Option", "Refund (USD)")
cost = Series("Refund", [12400, 8270, 0])
decision = Buttons([d1, d2, d3])
d1 = Button("Approve downgrade + $8,270", @ToAssistant("Approve partial refund", {task: "approve_partial", amount: 8270}), "primary")
```

It reads almost like pseudocode, which helps when you debug it. It is also cheap. In Thesys's own benchmark across seven UI scenarios, OpenUI Lang used 52.8% fewer tokens in total than the equivalent JSON, and up to 67% fewer on individual scenarios. Fewer tokens means faster first paint and lower cost, and both matter once an agent renders thousands of screens a day.

## Three workflows I tried

I picked three requests that come up in almost every company and that a text answer handles badly.

### 1. Sales: "Which Q4 deals over $50k are at risk this week?"

A text answer here is a long paragraph of account names and numbers that nobody can scan. The generated answer is a small dashboard: three KPI cards (at-risk value, silent champions, slipped close dates), a bar chart of exposure by risk signal, a sortable table of the six deals with owners, and a suggested next step. One button drafts check-in emails for the four silent champions, and the callout says plainly that nothing goes out without approval.

What changes for the reader: the sales leader can see the size of the problem and who owns each piece in a few seconds, then act without leaving the conversation.

### 2. IT onboarding: "Priya joins Monday as a data analyst in Finance. Get her set up."

Most of the answers already exist in the HR record. A chatbot would still ask the manager six questions, one message at a time. The generated answer shows the plan (accounts, laptop, data access, day one), pre-fills what it already knows, and asks only for the three choices a person has to make: laptop, which dashboards to grant, and an onboarding buddy. Restricted dashboards are labelled as needing extra approval. Required fields are validated by the renderer, not by the model, so the agent can't open tickets with half the information missing.

What changes for the reader: one screen and one click instead of a back-and-forth thread.

### 3. Support: a $12,400 refund above the agent's limit

This is the case I care most about. The agent is allowed to approve refunds up to $2,000, so it has to stop. Instead of a paragraph, it shows a warning that it needs a human and why, the facts it checked (contract terms, seat usage over 60 days, prior refunds, policy), a chart comparing three options, and a recommendation: downgrade to 20 seats and refund $8,270, which keeps the account and costs $4,130 less than a full refund.

Then three buttons. The click goes back to the agent as structured data, for example `{task: "approve_partial", amount: 8270}`, not as free text the agent has to interpret.

What changes for the reader: the approver sees the evidence and the trade-off before deciding, and the decision is recorded in a form a system can act on and audit.

## What this means for engineering leaders

Building the prototype took a few evenings. The more useful part was what it made me think about for teams putting agents in front of real users.

**The component library is your safety boundary.** The model can only use components you registered, with arguments you typed. It can't invent a "Delete account" button that you never built. That moves a lot of safety work from prompt wording, which is fragile, to a component list that you can review like an API. Design it with the same care, and version it.

**Actions should come back as data, not prose.** When a click returns `{task, amount}`, the agent doesn't have to guess what the person meant, and you get an audit trail almost for free. For anything involving money, access or customer commitments, this matters more than how nice the screen looks.

**Human-in-the-loop should be a designed screen.** Many agent rollouts treat approval as an afterthought: a Slack message, a "reply YES to continue". A good approval screen shows why the agent stopped, what it checked, what it recommends and what each option costs. That is product design work, and it deserves a real owner.

**Streaming changes how slow feels.** A screen that starts drawing in under a second feels faster than a complete answer that arrives after eight, even if the total time is the same. If your agents do slow, multi-system lookups, render progressively.

**It isn't the right tool everywhere.** Open questions, explanations and anything that is mostly reasoning still read better as text. Generated screens also need the same accessibility, testing and analytics as any other UI, and the tooling for that is young. I would start with one or two high-volume workflows that end in a decision, not with a platform rewrite.

## Can these screens run inside ChatGPT or Claude?

There is now a standard way to put interactive UI inside chat assistants: [MCP Apps](https://github.com/modelcontextprotocol/ext-apps), an official extension of the Model Context Protocol. An MCP server registers a tool together with a UI resource, and a supporting host renders that UI in a sandboxed frame next to the conversation. Claude and ChatGPT both support it.

I wrapped the OpenUI renderer as an MCP App, so the model can call a `render_openui` tool with an OpenUI Lang program, and button clicks come back into the chat as messages with the structured context attached. I tested it in the MCP Apps reference host, not in Claude or ChatGPT themselves. The picture below shows the same refund screen inside a generic chat app.

![The refund approval screen rendered inside a generic chat assistant through MCP Apps](/images/blog/agents-that-answer-with-screens/chat-host.webp)

For leaders, the interesting part is reach. You can build an approval screen once and show it in your own product and inside the assistants your teams already use, with the same component boundary in both places.

## Where I would start

If you run teams that ship agents, pick one workflow that ends in a human decision: a refund, an access request, a discount approval, an incident escalation. Write down what the approver needs to see to decide in under a minute. Then ask whether a paragraph is really the best way to show it.

Which workflow in your company would you rather approve with a button than a chat reply?
