An agent creates the rollout checklist. The external service accepts the request. The worker crashes before the agent records the result. When the worker restarts, what should it do?

A conversation summary might say, “Checklist creation was in progress.” That leaves the critical question open: did the write happen?

I’d give the operation a stable identity before sending it and keep a durable record of the intended action. On recovery, the worker should reconcile using that identity, either by looking up the prior result or retrying with an idempotency key that the downstream system honors.

The workflow needs a checkpoint for the goal and outstanding work. It also needs receipts for accepted side effects. That separation keeps the agent from inferring external state from its own text.

The test is straightforward: crash after the downstream service commits and before the local receipt is saved. Restart and check that the customer still has exactly one checklist. Repeat with a timeout and a concurrent retry.

### Follow the operation through the crash

| Boundary | What survives | Recovery behavior |
|---|---|---|
| Before the request leaves the worker | Stable operation ID and canonical payload | Dispatch the recorded intent |
| After provider commit, before local receipt | Intent locally and effect at the provider | Look up the effect or retry using the same ID |
| After the local receipt commits | Intent and receipt | Resume from the completed step |

I’d generate the operation ID from a persistent run and action identity before dispatch. Store the account, action, payload and expected preconditions. A retry must reuse the same identity and payload. If the user changes the intended target, create a new operation and resolve the old one first when its outcome is uncertain.

A local transaction can save workflow state and dispatch intent together. The downstream effect is still outside that transaction. Confirm that the provider actually honors the key across timeout and retry, what it returns on key reuse, and how long deduplication lasts. When the provider offers neither reliable lookup nor retry dedupe, mark the result unresolved and route it for reconciliation instead of issuing another consequential write automatically.

### Test the window that matters

Inject a timeout after the downstream commit, restart the worker, and run a second worker against the same intent. Verify the downstream count and the stored receipt. Also test reuse with a different payload and recovery beyond the provider’s key lifetime. Track duplicated effects and time spent in unresolved state separately from model response quality.

**Try it.** The SQLite example keeps its local intent across a simulated restart and reuses the provider’s receipt. The simulated provider is a fixture. Run the same failure injection against your real tool contract before publishing a reliability claim.

**Run the demo.** The fixture is [`examples/memory_demos.py`](https://github.com/abhishekramkrishna/agent-harness-lab/blob/main/examples/memory_demos.py) in agent-harness-lab. It runs offline, with no model or network calls, and asserts the behaviour described above.

## Conclusion

Treat an accepted side effect as a workflow event with an identity and a receipt. Test the crash window before trusting automatic retries on real accounts.
