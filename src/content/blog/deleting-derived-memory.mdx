A customer removes a memory item. The account fact disappears from the UI. A week later, the agent mentions the same detail from last month’s handoff summary.

If the summary can reconstruct the deleted fact, the memory feature needs a deletion model that knows where its derivatives came from.

I’d assign every persisted memory a source identity and track where it flows: semantic facts, summaries, embeddings, caches, and any queued rebuilds. A tombstone can make reads stop serving the source and its derivatives immediately. Background work can then purge or rebuild those artifacts according to their lifecycle. Rebuilds need to consult the tombstone too.

The regression test I’d run: delete one fact, replay an older event and start an indexing job that was already queued. Open a new session and ask the question that used to surface the fact. It should stay gone throughout the rebuild.

For product leaders, deletion behavior belongs in the feature spec next to “remember this.” Both affect whether users can trust the agent across sessions.

### Decide what “gone” means across the pipeline

Here’s the lifecycle I would specify for a removed onboarding preference:

| Copy | Expected behavior |
|---|---|
| Authoritative preference | Remove it from normal reads and record the deletion generation |
| Handoff summary and search entry | Block recall through lineage, then rebuild or purge |
| Cache | Invalidate it or require a generation check before serving |
| Queued extraction or indexing job | Reject writes derived from the deleted generation |
| Backup or exported copy | Apply the documented lifecycle and enforce deletion rules on restore |

The tombstone only works if the source identity survives normalization. When three facts get combined into one summary, keep links to the contributing records. If one contributor is deleted, hide that version and rebuild from the remaining authorized sources. For very large derived artifacts, decide up front how coarse lineage can be before deleting one item needlessly disrupts unrelated work.

### Verify immediate invisibility and eventual cleanup separately

First test whether a fresh session can surface the fact right after deletion. Then inspect derived copies once cleanup completes. Force the background job to start from an old snapshot. When it tries to commit, compare against the current deletion generation. Replay older evidence and verify that it does not recreate the deleted fact. Test restore behavior where backups are part of the product.

A customer asking to forget one thing should be able to predict what the next conversation will see. The product should also explain when background cleanup finishes and how separately managed copies are treated.

**Try it.** Delete the source behind a handoff summary. Test both visibility of the existing summary and the result of an attempted stale rebuild. The demo checks those behaviors in sequential execution.

**Run the demo.** The fixture is [`examples/memory_demos.py`](https://github.com/abhishekramkrishna/agent-harness-lab/blob/main/examples/memory_demos.py) in agent-harness-lab. It runs offline, with no model or network calls, and asserts the behaviour described above.

## Conclusion

Track lineage through every copy that can feed recall. Verify immediate invisibility and delayed cleanup independently, including rebuilds from old snapshots.
