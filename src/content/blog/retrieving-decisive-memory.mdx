A SaaS agent gets this request: “Can we enable the new widget for ACME-EU?”

Its search finds a good conversational match about rolling out widgets. It misses the one account record that says the EU pilot is sandbox-only.

I’d split that retrieval problem into three decisions:

1. Can this agent read the account record, and is it current?
2. Which record matches the exact account, environment, and feature?
3. What supporting context helps interpret the decision?

Use exact keys for the first lookup when the inputs are known. Use lexical and semantic retrieval for supporting evidence when terminology varies. Put a budget on what reaches the model and preserve the source IDs.

The detail I’d care about in the eval: did the right record reach the model before the tool call? If retrieval never supplied the authoritative restriction, a final-answer judge can tell you the result was wrong. The retrieval trace can tell you where to fix it.

### Make the retrieval contract visible in a trace

For the widget request, I’d log the canonical tenant, account and feature identifiers first. If “ACME” maps to both a US and an EU account, clarify the target before proposing a rollout. For a resolved target, the structured lookup should return the current environment restriction and its source ID. The supporting retrieval path can then add installation notes or similar rollout episodes.

| Stage | What I’d inspect |
|---|---|
| Candidate generation | Were filters applied before ranking? |
| Rank fusion and budget | Did exact identifiers and supporting terms survive? |
| Context assembly | Was the authoritative restriction included? |
| Tool gateway | Was the exact target checked against live policy? |

Lexical search helps with identifiers and product terminology. Semantic retrieval helps when “enable the widget” and “activate in-app guidance” describe the same intent. Rank fusion combines independent result lists. For the exact policy, use a dedicated structured lookup and preserve its priority through truncation. If the index is behind, query the authoritative store for consequential decisions.

### Debug retrieval with three different fixtures

Use one easy query with the exact feature ID, one paraphrase, and one query where current and retired accounts have nearly identical names. Record whether the right evidence was eligible, ranked and injected. Then give the agent the gold evidence directly. If that repairs the decision, inspect retrieval first. If the failure persists, inspect evidence interpretation and tool guardrails.

Measure recall at the actual context budget, not just at the retriever’s generous top-k. Track unauthorized results as a separate failure class and compare p95 latency after adding each search path.

**Try it.** Put a stale document and another tenant’s document at the top of both fixture lists. The authoritative policy and scoped supporting records should still be the only records returned.

## Conclusion

Put the decisive fact on a path that guarantees scope, freshness, and space in context. Grade the retrieval trace and the tool outcome so you can tell which stage needs fixing.
